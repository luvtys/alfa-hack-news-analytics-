# Контракт API — версия 1.1.0

Заморожен 20 октября 2026. Менять только через общий чат и с инкрементом
`contract_version` во всех ответах. Фронт и бэк проверяют соответствие
схемам в CI: `python3 validate_contract.py`.

## Что изменилось в 1.1.0 — 21 октября 2026

Одно решение команды по критерию приёмки 2: **при недостаточном качестве
данных система отказывается от вывода и называет причину, а не показывает
предупреждение рядом с цифрой.** Предупреждение оставляет неверный вывод на
экране, а вывод о зависимости от контрагента при покрытии ниже 20% неверен.

Что из этого следует для кода:

| Изменение | Где |
| --- | --- |
| Новый код `empty_reason.code` = `blocked_by_guard` + обязательный массив `blocked` | конверт `GET /api/insights` |
| Новое поле `data_quality.refused[]` — выводы, от которых система отказалась | `insight.schema.json` |
| Новое обязательное поле `relevance.scenario_id` | `insight.schema.json` |
| Правило 3 переписано: отказ вместо примечания | ниже |
| Новая фикстура отказа `insights_U_182712_CFO_blocked.json` | `fixtures/` |

Остальное в 1.1.0 совместимо с 1.0.0: поля не удалялись и не переименовывались.

Базовый путь `/api`. Везде `Content-Type: application/json; charset=utf-8`.

## GET /api/insights

Лента инсайтов для одного клиента в одной роли.

**Параметры**

| Имя | Тип | Обяз. | По умолчанию | Описание |
| --- | --- | --- | --- | --- |
| `u_id` | string | да | — | `U_106783` |
| `role` | enum | нет | `CFO` | `OWNER` \| `CFO` \| `CHIEF_ACCOUNTANT` |
| `limit` | int | нет | 10 | 1–50 |
| `since` | date-time | нет | −24ч | нижняя граница `event.published_at` |
| `min_score` | number | нет | 0.55 | порог релевантности |

**200 OK** — объект-конверт:

```json
{
  "contract_version": "1.0.0",
  "synthetic_u": "U_106783",
  "role_view": "CFO",
  "generated_at": "2026-10-20T09:12:00+03:00",
  "total": 1,
  "items": [ { "...": "объект Insight по insight.schema.json" } ]
}
```

**Пустая лента** — тот же конверт с `total: 0`, `items: []` и обязательным
блоком `empty_reason`. Это не ошибка, а штатное состояние, и фронт обязан его
рисовать: именно так выглядит контрольный пример на демо.

```json
{
  "empty_reason": {
    "code": "below_threshold",
    "message": "За последние сутки релевантных событий не найдено",
    "detail": "Проверено 214 новостей, ни одна не набрала порог 0,55. Ближайшая — 0,41.",
    "checked_events": 214,
    "best_score": 0.41,
    "threshold": 0.55,
    "nearest_event": { "headline": "...", "score": 0.41, "why_below": "..." },
    "trace_id": "trc_0a55fe"
  }
}
```

Коды `empty_reason.code`: `below_threshold`, `no_events`, `no_profile`,
`company_unknown`, `blocked_by_guard`.

**Отказ по качеству данных** — `blocked_by_guard`. Это не то же самое, что
`below_threshold`: там релевантного события не нашлось, здесь оно нашлось, но
данных для вывода недостаточно. Фронт обязан различать эти два состояния
визуально — на демо показываются оба.

```json
{
  "empty_reason": {
    "code": "blocked_by_guard",
    "message": "Сигнал найден, но данных для вывода недостаточно",
    "detail": "Крупнейший плательщик формирует 99,9% наблюдаемого входящего потока. Но банк наблюдает 3,2% выручки и трёх плательщиков, ни один из них не обслуживается в банке.",
    "threshold": 0.55,
    "blocked": [
      {
        "scenario_id": "counterparty_dependence",
        "guard": "flow_coverage",
        "message": "Наблюдаемый поток покрывает менее 20% выручки — вывод о зависимости недостоверен",
        "missing_field": "observed_flow_to_revenue",
        "observed": { "flow_coverage_tier": "negligible", "observed_flow_to_revenue": 0.032 },
        "event": { "headline": "...", "published_at": "...", "event_type": "sector_demand" }
      }
    ],
    "trace_id": "trc_4c81de"
  }
}
```

В `blocked[]` обязательны `scenario_id`, `guard`, `message`; `missing_field`,
`observed` и `event` опциональны и нужны, чтобы фронт мог показать, какое
событие и какого поля не хватило. `guard` принимает `flow_coverage`,
`known_counterparty`, `group_structure` — это идентификаторы из
`scoring/scenarios.yaml`, их же пишет трасса.

Фикстуры: `fixtures/insights_U_106783_CFO.json`, `insights_U_26030_CFO.json`,
`insights_U_1941_CFO.json`, `insights_U_4601_CFO_empty.json`,
`insights_U_182712_CFO_blocked.json`.

## POST /api/chat

Уточняющий вопрос по клиенту или по конкретному инсайту.

```json
{
  "u_id": "U_106783",
  "role": "CFO",
  "question": "А кто у нас второй по размеру плательщик?",
  "insight_id": "ins_20261020_U_106783_001",
  "history": [ { "role": "user", "content": "..." }, { "role": "assistant", "content": "..." } ]
}
```

**200 OK**

```json
{
  "contract_version": "1.0.0",
  "answer": "текст ответа",
  "evidence": [ { "id": "e1", "kind": "verified_fact", "ref": "db://...", "label": "..." } ],
  "insufficient_data": false,
  "trace_id": "trc_9d02aa"
}
```

`insufficient_data: true` означает, что агент не нашёл подтверждения и ответил
«данных нет». Фронт в этом случае не показывает блок evidence.

## GET /api/trace/{trace_id}

История шагов агента. Описана в `trace.schema.json`.
Фикстура: `fixtures/trace_trc_8f21ab.json`.

Фронт рисует шаги **только** из этого ответа. Захардкоженная анимация
«Анализирую контрагентов…» без реального вызова — прямое невыполнение
критерия 12: жюри проверяет трассируемость восстановлением источников.

Поле `status` у шага:

| Значение | Как рисовать |
| --- | --- |
| `ok` | обычный шаг |
| `empty` | шаг выполнен, данных нет — серым |
| `failed` | критик забраковал, дальше идёт `retry` — красным, с текстом `note` |
| `superseded` | источник отброшен как устаревший — показать `note` |

Шаги с `agent: "critic"` и `action: "retry"` — главный визуальный аргумент
демо: видно, что агент сам себя поймал. В фикстуре это шаги 7 и 8.

## Ошибки

```json
{ "contract_version": "1.0.0", "error": { "code": "company_unknown", "message": "..." } }
```

| HTTP | code |
| --- | --- |
| 400 | `bad_request` |
| 404 | `company_unknown` |
| 429 | `budget_exceeded` — лимит токенов исчерпан |
| 503 | `model_unavailable` |

`budget_exceeded` фронт показывает отдельным баннером, а не как общую ошибку:
на демо это вероятный сценарий, и он не должен выглядеть как падение.

## Три правила, которые нельзя нарушать

1. **Числа приходят готовыми.** Бэкенд не отдаёт фронту сырые строки для
   пересчёта: доли, суммы, покрытие считаются в витрине и приходят в
   `features_used` и `data_quality`.
2. **Каждое утверждение имеет `evidence_id`.** Фронт рендерит бейдж по
   `evidence[].kind`: `verified_fact` — данные банка, `alfa_view` — цитата
   аналитики с датой, `news` — внешняя ссылка, `model_inference` — вывод
   модели, визуально слабее остальных.
3. **При недостаточном покрытии — отказ, а не предупреждение.** Решение
   команды от 21 октября 2026 (критерий приёмки 2). Разворачивается в три
   конкретных требования:

   - Бэкенд **не формирует** вывод о зависимости от контрагента при
     `flow_coverage_tier` = `low` или `negligible`. Не формирует с оговоркой,
     не формирует с пониженной уверенностью — не формирует. Если по клиенту
     больше нечего показать, лента пустая с кодом `blocked_by_guard`.
   - Если у клиента есть другой валидный инсайт, а сценарий зависимости был
     заблокирован, отказ едет в `data_quality.refused[]` этого инсайта.
     Фронт рисует его **отдельным блоком «вывод не сделан»** с причиной из
     `message`, а не сноской под цифрой.
   - `data_quality.notes` остаётся и при `low`/`negligible` обязателен, но
     его задача — объяснить ограничение выборки, а не подпереть вывод,
     который на ней делать нельзя.

   Почему так: предупреждение рядом с неверным выводом оставляет неверный
   вывод на экране, и пользователь запоминает цифру, а не сноску. Проверяется
   машиной — `validate_contract.py` падает, если сценарий
   `counterparty_dependence` выдан при тонком покрытии.
