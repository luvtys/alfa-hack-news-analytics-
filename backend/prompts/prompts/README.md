# Системные промпты четырёх режимов

```
00_shared.md        общий блок: девять правил, инструменты, качество данных
01_planner.md       план вызовов инструментов
02_analyst.md       интерпретация и evidence
03_critic.md        самопроверка по чек-листу
04_writer.md        переписывание под роль
build_prompts.py    сборка: общий блок + блок режима
test_prompts.py     22 проверки, включая проверку самих few-shot
few_shot/           профили демо-компаний, выгруженные из витрины
```

```bash
python3 build_prompts.py --out build     # собрать четыре файла
python3 build_prompts.py --mode analyst  # напечатать один
python3 test_prompts.py ../datamart/out
```

## Бюджет

| Режим | Модель | Токенов |
| --- | --- | --- |
| Планировщик | Qwen3.6 35B A3B | ~2 590 |
| Аналитик | DeepSeek-V4.1-Flash | ~3 121 |
| Критик | Qwen3.6 35B A3B | ~2 917 |
| Редактор | Gemma 4 26B A4B | ~2 554 |

На один инсайт грузятся три из четырёх: планировщик, аналитик и критик —
около 8 600 токенов системных промптов плюс данные. Редактор подключается
отдельно и только при смене роли, поэтому в стоимость одного инсайта он
входит не всегда. Оценка грубая, 3,1 символа на токен: токенизатора Qwen под
рукой нет, погрешность порядка 10%.

## Почему правила пронумерованы

Критик ссылается на номер, трасса сохраняет номер нарушенного правила, а на
демонстрации видно не «модель себя проверила», а «модель поймала нарушение
П4 и переписала формулировку». Разница между этими двумя фразами и есть
критерий 12.

Девять правил: числа не вычисляются, у каждого утверждения есть тип, пустое
поле означает «данных нет», платежи не выручка, признак ключевого
собственника не риск, актуальность источника проверяется, инвестрекомендаций
нет, структура группы проверяется, ответ строго JSON.

## Few-shot на реальных данных

Примеры построены на двух компаниях из витрины, а не на выдуманных.

`U_106783` — производство электрической распределительной аппаратуры,
Москва, выручка 20,829 млрд, лизинг, зарплатный проект, импорт из ОАЭ,
Китая и Литвы, 633 плательщика, на крупнейшего приходится 75,47%
наблюдаемого потока при покрытии выручки 60,88%. Это положительный пример:
полный инсайт с тремя последствиями, позицией банка и честно вынесенным
допущением модели.

`U_4601` — оптовая торговля мясом, Санкт-Петербург, выручка 16,86 млрд,
банк видит 71% выручки, 329 плательщиков, на крупнейшего приходится 5,1%.
Это отрицательный пример в промпте критика: черновик, который заявляет
зависимость от покупателя там, где её нет. Критик находит семь дефектов со
ссылками на номера правил.

Отрицательный пример важнее положительного. Модель, видевшая только
правильные ответы, не умеет распознавать неправильные, а именно это работа
критика.

## Что проверяет тест

Главное: **few-shot обязаны подчиняться правилам, которым учат.** Пример,
нарушающий П1, учит модель нарушать П1, и никакой инструкцией это потом не
лечится.

Поэтому проверяется, что каждое число в выходе примера аналитика выводимо
из входа — тождественно либо округлением доли до процентов, других
преобразований П1 не допускает. Что все `evidence_ids` существуют, у каждой
цитаты аналитики есть дата, а допущение модели вынесено в `model_inference`.
Что формулировки «доля выручки» нет в примерах ответов — но есть в примере
критика как разбираемый дефект. Что у главбуха не появилось чисел, которых
нет у финдиректора. Что профили в примерах посимвольно совпадают с витриной
и контрольная компания действительно без концентрации.

Два теста из этого набора сначала упали на моих собственных ошибках:
экстрактор чисел разбирал горизонт `3-6M` как числа 3 и −6, а запрещённую
формулировку искал во всём промпте, включая текст самого правила, которое её
запрещает. Это к вопросу о том, зачем в принципе писать проверки на
промпты — глазами такое не ловится.

## Связь с остальным

Выход аналитика — это объекты `interpretation` и `evidence` из
`insight.schema.json`. Выход редактора ложится в `headline` и `actions`.
Выход критика идёт в трассу шагами с `agent: "critic"`, а цикл `fail` →
`retry` → `pass` виден на фронте.

Правило для роли `CHIEF_ACCOUNTANT` — только последствия с
`confidence: high` и пустой `model_inference` — реализовано и здесь, и в
`role_multiplier` конфига сценариев. Два уровня одной защиты: сценарий может
не попасть в ленту бухгалтера, а если попал, текст всё равно очищается.
