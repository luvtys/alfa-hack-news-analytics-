# Правила сценариев для score_relevance

Четыре золотых сценария вынесены в конфигурацию. Ни одного обращения к
языковой модели: скоринг детерминирован, объясним и стоит ноль токенов.

```
scenarios.yaml       четыре сценария: триггеры, аудитория, guard-ы, компоненты
score_relevance.py   движок: мини-язык условий + расчёт пяти компонент
test_scenarios.py    прогон на реальной витрине, 16 проверок
```

```bash
pip install pyyaml pandas pyarrow
python3 test_scenarios.py ../datamart/out
```

## Как считается

Для пары «компания + событие»:

1. **triggers** — подходит ли событие сценарию. Нет — сценарий молчит.
2. **audience** — подходит ли компания. Нет — сценарий молчит.
3. **guards** — хватает ли качества данных. Либо блок, либо штраф к баллу.
4. **components** — пять компонент 0..1 по правилам из конфига.
5. `score = Σ weight × component × role_multiplier − penalties`
6. `score ≥ threshold` — событие попадает в ленту.

Первое сработавшее правило компоненты выигрывает, поэтому порядок правил в
YAML — это приоритет, видимый без чтения кода.

Метод `to_contract()` отдаёт готовый объект `relevance` из
`insight.schema.json`: балл, порог, разложение по пяти компонентам и строка
объяснения. На вопрос «почему эта новость наверху» есть точный ответ.

## Что показал прогон на 85 513 профилях

| Сценарий | Событие-триггер | В ленте | Доля базы |
| --- | --- | --- | --- |
| Стоимость долга | решение по ставке | 5 748 | 6,7% |
| Импорт и валюта | прогноз курса юаня | 7 490 | 8,8% |
| Зависимость от контрагента | данные по инвестициям | 5 046 | 5,9% |
| Спрос и ФОТ | данные по рознице | 3 609 | 4,2% |

Пересечение между сценариями — от 3% до 14%: они отбирают разные компании,
а не четыре раза одну и ту же выборку.

Нерелевантные события — обзор рынка золота и спортивная новость — не
поднимают ни одного сценария ни у одной компании.

Баллы различимы: по событию о ставке медиана 0,49 при p90 0,59, по событию
об инвестициях медиана 0,55 при p90 0,70. Лента ранжируется, а не
высыпается в случайном порядке.

## Два решения, которые стоит знать

**Guard по качеству данных в сценарии зависимости.** Доля топ-1 плательщика
выше 50% есть у 14 123 компаний, но у 8 582 из них банк видит меньше 20%
выручки. Такой вывод формально верен и практически бесполезен. Сценарий
блокируется, если `flow_coverage_tier` ниже `medium`. На выборке из 400
компаний со слабым сигналом ни одна не дошла до ленты.

**Сигналы уровня группы засчитываются только при подтверждённой структуре.**
Первая версия конфига ловила компании по флагу «у группы есть кредит» без
проверки `grp_group_structure_suspect` — и затаскивала в аудиторию 72 тысячи
компаний вместо 29 тысяч. Блок идентификаторов `group_1340xx`–`group_1347xx`
устроен иначе остальных, и по нему групповые флаги ничего не значат.

## Роли

`role_multiplier` меняет балл под роль. Пример: сценарий зависимости от
контрагента для `U_106783` даёт 0,80 собственнику и финдиректору и 0,48
главбуху — в его ленту он не попадает. Это механическая реализация правила
«главбуху только подтверждённые последствия» из продуктовых идей.

## Чего здесь нет и не будет

Сценарного режима «Что если». В витрине есть бинарные метки продуктов, но
нет ни суммы долга, ни ставки по нему, ни структуры портфеля. Качественная
оценка чувствительности возможна, денежная — нет. Это ограничение данных, а
не нереализованная функция, и формулировать его надо именно так.

## Связь с остальными артефактами

Поля профиля берутся из `company_profile` витрины. Списки в
`evidence_required` говорят агенту, какие инструменты и какие документы
корпуса он обязан вызвать до формулировки вывода: например, сценарий
стоимости долга требует проверить временной ряд `key_rate_end_2026_forecast`,
потому что в корпусе лежат пять версий этого прогноза и три из них устарели.

Фикстуры в `contracts.zip` пересчитаны по этому конфигу: баллы в них
совпадают с тем, что выдаёт движок.
