# VOLTURI — передача бизнес-аналитики в разработку

**Дата: 21 октября 2026. Контракт: 1.1.0. Состояние: готово к интеграции.**

Это не документация к будущей системе, а шесть рабочих артефактов, каждый из
которых запускается одной командой и выдаёт результат на реальных данных
кейса. Числа ниже воспроизводятся прогоном, а не взяты из презентации.

Чего от вас нужно: не переписывать контракт и конфиг сценариев, а подключить
их. Всё, что в разделе «Заморожено», менять только через общий чат — иначе
фронт и бэк разойдутся за полдня до демо.

## 1. Карта пакета

| Архив | Что внутри | Кому в первую очередь | Что с ним делать |
| --- | --- | --- | --- |
| `datamart.zip` | 6 готовых таблиц parquet, `build_datamart.py`, `schema.sql`, `load.sh`, 9 проверок целостности | бэкенд, данные | читать профили из `company_profile.parquet` сразу; для PostgreSQL — пересобрать (см. ниже) |
| `contracts.zip` | `insight.schema.json`, `trace.schema.json`, `api_contract.md`, `validate_contract.py`, 6 фикстур | бэкенд **и** фронтенд | фронт верстает по фикстурам, не дожидаясь API; оба ставят валидатор в CI |
| `scoring.zip` | `scenarios.yaml`, `score_relevance.py`, `test_scenarios.py` | бэкенд | вызывать `Scorer.score(profile, event, role)` на каждой паре до обращения к модели |
| `prompts.zip` | `00_shared.md` + 4 системных промпта, few-shot, `build_prompts.py`, `test_prompts.py` | бэкенд (агент) | собрать промпты сборщиком, не редактировать руками |
| `corpus_preprocessing.zip` | `build_corpus.py`, `corpus_registry.json`, `alfa_corpus_facts.json`, 4 бэкенда распознавания | бэкенд (RAG) | один раз распознать корпус, дальше читать из кэша; показатели брать из справочника, а не из распознанного текста |
| `golden.zip` | `golden_set.yaml`, `holdout.yaml`, `run_golden.py`, `check_insight.py` | все | гонять перед каждым коммитом в main |

**Две оговорки по `datamart.zip`, чтобы не спотыкаться на первом шаге.**
Во-первых, он идёт без `payment_edges.parquet` (1 380 432 ребра, 21 МБ) и без
крупных CSV-выгрузок — всё это восстанавливается `build_datamart.py` из трёх
исходных CSV кейса за пару минут. Во-вторых, `out/load.sh` грузит в PostgreSQL
именно из CSV, которых в архиве нет: до пересборки он не заработает. Наши
скрипты (`test_scenarios.py`, `run_golden.py`) читают parquet напрямую и
работают из архива как есть — PostgreSQL нужен вам, а не им.

## 2. Первые два часа

```bash
# 1. Витрина — она УЖЕ собрана, в архиве лежит готовый out/
unzip datamart.zip && cd datamart
pip install pandas pyarrow
ls out/                      # 6 таблиц parquet + schema.sql + load.sh + manifest.json

# Пересборка нужна в двух случаях: вам нужен PostgreSQL или нужен граф платежей.
# Положите три CSV кейса в ./src и прогоните:
python3 build_datamart.py --data ./src --out ./out    # 7 таблиц, ~2 мин
python3 make_ddl_and_validate.py out                 # 9 проверок, все должны пройти
DB_URL=postgres://user:pass@host/db bash out/load.sh out

# 2. Контракт — ставится в CI сразу, до первой строки бэкенда
unzip contracts.zip && cd contracts
pip install jsonschema
python3 validate_contract.py                          # 6 фикстур, контракт 1.1.0

# 3. Отбор
unzip scoring.zip && cd scoring
pip install pyyaml
python3 test_scenarios.py ../datamart/out             # охват, баллы, guard-ы, роли

# 4. Проверка качества
unzip golden.zip && cd golden
python3 run_golden.py --datamart ../datamart/out --scoring ../scoring
```

Если любая из четырёх команд падает — это не ваша ошибка интеграции, это
расхождение с тем, что сдавала аналитика. Пишите в чат, разберём.

## 3. Как это работает: четыре ступени

1. **Парсер** приносит событие (РБК, Росстат, ЦБ РФ) и нормализует сущности.
   Спецификация полей, дедупликации и офлайн-снапшота — в рабочем документе БА.
2. **Отбор.** `Scorer.score(profile, event, role)` → список `ScenarioScore`.
   Детерминированно, ноль токенов, работает по всем 85 513 профилям за минуты.
   Проходит порог 0,55 — событие идёт дальше. Не проходит — молчим, и в трассу
   пишется, почему.
3. **Агент.** Планировщик → аналитик → критик → редактор. Критик возвращает
   работу на доработку; retry-цикл виден в трассе.
4. **Выдача.** `GET /api/insights` — конверт по `api_contract.md`. Числа
   приходят готовыми: фронт ничего не пересчитывает.

**Ключевое правило архитектуры:** модель вызывается только на парах, прошедших
детерминированный порог. Под одно событие это 3 609–7 490 компаний из базы, а
в ленту одной роли попадают единицы. Это держит и качество, и бюджет 500 ₽.

## 4. Критерии приёмки

Шесть пунктов. Пятый и шестой проверяются машиной, остальные — глазами на
демо-прогоне.

1. **Доля топ-1 плательщика считается только по внешнему входящему потоку.**
   Слой `self` (81,67% объёма платежей!) и `intragroup` в расчёт не входят.
2. **При недостаточном покрытии — отказ, а не предупреждение.** Решение
   команды от 21.10.2026. Разворачивается так: бэкенд не формирует вывод о
   структуре покупателей при `flow_coverage_tier` = `low` или `negligible`;
   отказ уходит в `data_quality.refused[]`, а если валидных инсайтов не
   осталось — лента пустая с `empty_reason.code` = `blocked_by_guard`; фронт
   рисует это **отдельным блоком «вывод не сделан»** с причиной, а не сноской
   под цифрой. Образец ответа: `fixtures/insights_U_182712_CFO_blocked.json`.
3. **Без релевантного события система не выдаёт сигнал за новостную
   аналитику.** Диагностический признак сам по себе в ленту не попадает:
   сначала `triggers` по событию, потом `audience` по компании.
4. **Отсутствующие данные не подменяются догадками.** Поля из
   `client.features_missing` агенту упоминать запрещено.
5. **У каждого существенного утверждения есть ссылка на источник.**
   Проверяется `check_insight.py`.
6. **Интерфейс показывает реальные этапы обработки, а не имитацию «мыслей»
   модели.** Трасса — это шаги со статусами `ok`, `empty`, `failed`,
   `superseded` и расходом токенов, не анимация.

## 5. Заморожено — и что ваше

**Заморожено. Менять только через общий чат с инкрементом версии:**

- `insight.schema.json`, `trace.schema.json`, конверт и коды ошибок из
  `api_contract.md`;
- пять компонент релевантности, их веса, порог 0,55, множители роли;
- идентификаторы сценариев: `cost_of_debt`, `fx_import`,
  `counterparty_dependence`, `demand_and_payroll`;
- идентификаторы guard-ов: `flow_coverage`, `known_counterparty`,
  `group_structure`;
- правила П1–П9 в `prompts/00_shared.md`;
- `golden_set.yaml` и `holdout.yaml`.

**Ваше, правьте свободно:**

- любая реализация внутри: язык, фреймворк, кэш, очереди, схема БД поверх
  `schema.sql`;
- выбор моделей и провайдера (в `build_prompts.py` модели указаны как
  ориентир по размеру контекста, не как требование);
- вёрстка, компоновка, анимации — всё, что не меняет смысл полей;
- бэкенд распознавания корпуса: `text`, `tesseract`, `vlm`, `mock`;
- `few_shot`-примеры можно дополнять, но не удалять существующие.

## 7. Чего делать не надо

- **Не подкручивайте пороги под `holdout.yaml`.** Файл открывается один раз,
  в четверг вечером, после заморозки кода. Прогон делает один человек,
  результат идёт в питч как есть, включая провал. Подгонка под holdout
  лишает нас единственной честной метрики, и это видно по первому вопросу.
- **Не пересчитывайте доли и суммы на фронте.** Всё приходит готовым в
  `features_used` и `data_quality`. Пересчёт на клиенте — это второй источник
  правды и расхождение на демо.
- **Не используйте групповые признаки по блоку `group_1340xx`–`group_1347xx`.**
  253 из 341 крупной группы там: медиана 121 юрлицо против 5, десять
  отраслевых разделов против одного. Признак `grp_group_structure_suspect`
  уже стоит в профиле, конфиг сценариев его учитывает — просто не обходите.
- **Не считайте граф платежей без фильтра по слою.** 81,67% объёма — переводы
  компании самой себе. Неочищенный граф даёт бессмысленные выводы.
- **Не редактируйте собранные промпты из `build/` руками.** Правьте источники
  и пересоберите, иначе правка потеряется на следующей сборке.
- **Не берите прогнозные значения из распознанного текста корпуса.** Прогноз
  ключевой ставки на конец 2026 года существует в корпусе в пяти версиях:
  13,5% встречается трижды и устарел, актуальна одна запись — 14,0% от
  11 сентября. Поиск по смыслу выдаст любую из пяти с равной уверенностью.
  Показатели берутся из `alfa_corpus_facts.json` → `indicator_timelines`,
  только запись со `status: current`, и всегда вместе с её датой. Документ
  `russian_steels` в индекс не входит вообще — он устарел на пять лет, в
  реестре помечен `exclude_from_index`.
- **Не выдумывайте денежную оценку риска.** В данных нет ни суммы долга, ни
  ставки, ни срока. Качественная чувствительность — да, цифра потерь — нет.

## 8. Чего в данных нет

Чтобы никто не планировал функцию, под которую нет полей:

| Нет | Следствие |
| --- | --- |
| Сумма долга, ставка, срок, структура портфеля | режим «что если» в деньгах невозможен; только качественная оценка |
| Полный оборот компании | у 33 320 из 60 562 компаний банк видит менее 5% выручки; по ним выводы о контрагентах заблокированы |
| Подтверждённая структура групп везде | по блоку `134xxx` групповые сигналы не используются |
| Отраслевая принадлежность внешних плательщиков | в среднем около двух третей плательщиков вне периметра банка |
| `AMOUNT_WORKERS_SPARK_GRADATION` заполнено на 0,2% | численность берём только из `AMOUNT_WORKERS_FNS_GRADATION` |
| `FTS_COUNTRY_NAME` заполнено на 9,8% по базе и на 50,4% по крупным | валютный сценарий это терпит: без страны `factor_exposure` падает на значение по умолчанию 0,5 и сценарий всё равно работает по `FTS_FLAG`. Но «страна закупки» в карточке появляется только у половины импортёров — не планируйте её как обязательное поле UI |

## 9. Открытые вопросы

**К постановщику кейса** (если будет возможность спросить):

1. Что означает `GROUP_ID` в блоке `group_1340xx`–`group_1347xx` — это группа
   в том же смысле, что остальные, или технический контейнер?
2. Платежи в выгрузке — только через Альфа-Банк или весь оборот компании?
3. Будет ли обогащена градация `AMOUNT_WORKERS_SPARK_GRADATION`?

**Внутри команды, закрыть до репетиции:**

4. Точные URL лент РБК, Росстата и ЦБ РФ и формат дат в них.
5. Есть ли в зале сеть. Если нет — парсер работает со снапшота, проверить
   заранее, а не на сцене.
6. Кто держит ключ к модели и смотрит счётчик расхода. Один человек.
7. Фронт: кто верстает блок отказа по критерию 2. Это новая вёрстка,
   появившаяся 21 октября, её нет в макетах от 20-го.
